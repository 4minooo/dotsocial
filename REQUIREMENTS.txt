너는 웹 게임 개발과 실시간 멀티플레이 구현에 능숙한 개발자다.

아래 요구사항을 바탕으로 브라우저에서 실행되는 3D 소셜 웹 앱을 개발해줘.
한 번에 모든 기능을 대충 구현하지 말고, 단계별로 구현하고 검증해줘.

이번 첫 응답에서는 코드를 작성하지 말고 다음 내용을 먼저 제안해줘.
1. 요구사항 정리와 기본 가정
2. 기술 구조와 선정 이유
3. 화면 구성과 사용자 흐름
4. Firebase 데이터 구조와 보안 설계
5. 무료 요금제에서의 제약과 트래픽 예상
6. 단계별 개발 계획과 각 단계의 완료 기준

필수적으로 결정해야 하는 사항만 질문하고, 나머지는 합리적인 기본값을 제안해줘.
내가 개발 시작을 요청하면 아래 단계 순서대로 구현해줘.

[1. 앱의 목적]

사용자가 작은 3D 도트 그래픽 공간에 접속하여,
캐릭터를 움직이며 다른 사용자와 채팅하고 미니게임을 즐기는 웹 앱이다.

핵심 경험:
홈에서 캐릭터 꾸미기 → 맵 선택 → 입장 →
다른 사람과 이동·채팅·이모트 → 미니게임 → 퇴장 또는 맵 변경.

초기 버전은 소규모 비상업적 서비스로 개발한다.
PC 브라우저와 키보드 조작을 우선 지원한다.

[2. 기술과 배포 조건]

기본 기술:
- React + TypeScript + Vite
- Three.js + React Three Fiber
- Firebase Authentication의 익명 인증
- Firebase Realtime Database
- GitHub 저장소
- Vercel Hobby에 프런트엔드 배포

설계 조건:
- Firebase는 Spark 무료 요금제를 유지한다.
- 결제 계정 연결이나 Blaze 전환을 전제로 구현하지 않는다.
- Cloud Functions, Cloud Storage, 유료 API를 사용하지 않는다.
- 별도의 상시 실행 서버나 WebSocket 서버를 요구하지 않는다.
- 실시간 데이터는 브라우저에서 Firebase SDK로 동기화한다.
- 5개의 서버는 하나의 Firebase 프로젝트 안에 있는 논리적 방이다.
- 맵과 캐릭터 에셋은 프로젝트의 정적 파일이나 코드로 구성한다.
- 이동처럼 빈번한 데이터를 Firestore에 기록하지 않는다.
- 무료 한도 안에서 무제한 운영할 수 있다고 가정하지 않는다.
- 구현 시작 시 공식 문서로 무료 요금제와 라이브러리 호환성을 확인한다.

기술 변경이 필요하면 이유와 무료 배포 조건에 미치는 영향을 설명한다.

[3. 그래픽과 분위기]

실제 3D 공간에 복셀 캐릭터와 소품을 배치한다.
2D 화면에 그림자만 추가한 형태로 대체하지 않는다.

시각적 방향:
- 작은 블록으로 구성된 귀여운 캐릭터
- 픽셀 느낌의 텍스처와 낮은 렌더링 해상도
- 고정된 사선 시점의 직교 카메라
- 명확하게 구분되는 바닥, 벽, 가구, 장식
- 차분하고 친근한 색감
- 캐릭터 방향과 걷기 동작을 알아보기 쉽게 표현
- 한국어 UI와 읽기 쉬운 글꼴

도트 느낌은 3D 월드에 적용한다.
채팅, 버튼, 닉네임은 선명하게 읽을 수 있어야 한다.

고해상도 모델, 무거운 후처리, 과도한 실시간 그림자는 피한다.
첫 공원 맵에서 그래픽 방향과 성능을 검증한 후 다른 맵으로 확장한다.

[4. 홈 화면]

홈에서 다음을 설정한다.
- 닉네임
- 헤어 스타일
- 헤어 색
- 상의 색
- 하의 색
- 기본 액세서리 선택
- 캐릭터 3D 미리보기
- 입장할 맵 선택
- 맵별 현재 접속 인원
- 입장 버튼

외형은 제공된 프리셋과 색상 중에서 선택한다.
사용자 이미지 업로드는 초기 버전에 포함하지 않는다.

닉네임은 공백 제거 후 2~12자로 제한한다.
한글·영문·숫자를 지원하고 표시할 때 안전하게 처리한다.

캐릭터 설정은 새로고침 후에도 유지한다.
익명 계정은 브라우저 저장 정보 삭제 시 유지되지 않을 수 있음을 안내한다.
닉네임 중복은 허용하며 실제 사용자 식별에는 Firebase UID를 사용한다.

[5. 맵과 입장]

초기 맵:
1. 공원: 잔디, 나무, 산책로, 벤치
2. 옥상: 난간, 화분, 휴식 공간, 도시 배경
3. 사무실: 책상, 의자, 회의 공간
4. 카페: 테이블, 카운터, 실내 장식
5. 해변: 모래, 바다 배경, 파라솔

맵마다 독립된 참가자, 채팅, 미니게임 상태를 갖는다.
다른 맵의 실시간 데이터는 구독하지 않는다.

초기 운영 목표는 방당 최대 8명으로 둔다.
이 목표가 무료 사용량을 보장하는 것은 아니며,
트래픽 계산과 검증 결과에 따라 조정할 수 있게 한다.

입장은 동시 요청을 고려한다.
정원이 찬 경우 안내하고 다른 맵을 선택할 수 있게 한다.
정원 처리가 UI에만 의존하는지, 데이터 규칙에서도 보호되는지 구분한다.

맵 변경 시 이전 방의 참가 상태와 구독을 정리한다.
새로고침, 중복 탭, 연결 끊김으로 유령 참가자가 남지 않도록 설계한다.

[6. 이동과 카메라]

- 방향키로 바닥 위를 이동한다.
- 화면 기준 방향과 이동 방향이 자연스럽게 대응한다.
- 대각선 이동이 더 빠르지 않도록 속도를 보정한다.
- 프레임 속도와 무관하게 동일한 이동 속도를 유지한다.
- 벽, 가구, 맵 경계와 충돌한다.
- 걷는 방향으로 캐릭터가 회전한다.
- 채팅 입력이나 모달에 포커스가 있으면 이동하지 않는다.
- 창 포커스를 잃으면 눌린 키 상태를 초기화한다.

내 캐릭터는 즉시 반응하게 한다.
다른 캐릭터는 수신된 위치 사이를 보간하여 자연스럽게 표시한다.

위치는 매 프레임 전송하지 않는다.
이동 중 초당 약 5회부터 시작하여 검증하고,
정지 상태에서는 불필요한 위치 쓰기를 하지 않는다.
정지 직후에는 마지막 위치를 동기화한다.

연결 상태, 재연결, 입장 실패를 사용자에게 표시한다.

[7. 채팅]

- 같은 맵에 있는 사용자끼리 전체 채팅을 한다.
- 화면에 채팅 패널을 제공한다.
- 캐릭터 위에 짧게 유지되는 말풍선을 표시한다.
- Enter로 입력창에 진입하고 메시지를 전송한다.
- 한글 IME 조합 중 Enter는 전송으로 처리하지 않는다.
- 메시지는 최대 200자로 제한한다.
- 빈 메시지와 연속 도배를 제한한다.
- 사용자별 음소거 기능을 제공한다.
- 메시지는 HTML이 아닌 일반 텍스트로 렌더링한다.

최근 메시지만 제한적으로 구독한다.
조회 개수 제한과 데이터 삭제는 다른 문제임을 고려하여,
채팅 데이터가 무한히 쌓이지 않도록 저장 상한과 정리 방식을 설계한다.

Cloud Functions나 예약 작업 없이 가능한 방식을 선택하고,
클라이언트 기반 정리의 한계도 문서화한다.

초기 버전에는 귓속말, 이미지 전송, 음성 채팅을 포함하지 않는다.

[8. 이모트]

기본 이모트:
- 손 흔들기
- 놀라기
- 기뻐하기

버튼 또는 단축키로 실행한다.
캐릭터 동작과 머리 위 표시를 함께 사용한다.
다른 사용자에게 이모트 종류와 시작 시점을 동기화한다.
짧은 재사용 대기시간을 둔다.

애니메이션 프레임 전체를 네트워크로 전송하지 않는다.

[9. 미니게임]

같은 맵의 다른 사용자에게 게임을 제안할 수 있다.
초대 → 수락 또는 거절 → 진행 → 결과 → 종료 흐름을 구현한다.
한 사용자는 동시에 하나의 게임에만 참가한다.

가위바위보:
- 1대1 단판
- 양쪽 선택이 완료된 후 결과 공개
- 무승부 처리
- 선택 제한 시간
- 상대 퇴장 또는 연결 끊김 처리
- 재대결 제안
- 선택을 먼저 제출한 사람의 패를 상대가 미리 읽을 수 없게 한다.
- 필요하면 임의값을 포함한 해시 커밋과 공개 방식을 사용한다.
- 클라이언트 구현만으로 보장할 수 없는 공정성은 명시한다.

오목:
- 15×15 판
- 흑 선공, 번갈아 한 수씩 진행
- 금수 없는 자유룰로 양쪽 모두 5개 이상 연결하면 승리
- 빈칸에만 착수 가능
- 차례가 아닌 사용자의 착수 금지
- 승리, 무승부, 기권, 상대 이탈 처리
- 중복 착수와 동시 요청으로 상태가 꼬이지 않게 한다.

승패와 착수 유효성은 테스트 가능한 순수 함수로 분리한다.
클라이언트 검증과 Firebase Security Rules의 역할을 구분한다.
참가자가 아닌 사용자가 게임 상태를 수정할 수 없게 한다.

초기 버전에는 랭킹, 재화, 보상, 경쟁전, 관전을 포함하지 않는다.

[10. 데이터와 보안]

Firebase Security Rules를 실제로 작성하고 에뮬레이터로 검증한다.
전체 공개 읽기·쓰기로 출시하지 않는다.

최소 검증:
- 인증된 사용자만 필요한 데이터에 접근
- 본인 프로필과 이동 상태만 수정
- 닉네임 길이와 외형 프리셋 검증
- 위치 범위와 데이터 타입 검증
- 채팅 작성자 UID와 인증 UID 일치
- 메시지 길이와 허용 필드 검증
- 미니게임 참가 권한과 상태 변경 권한 검증
- 가능한 범위에서 게임 차례와 제출 상태 보호

onDisconnect와 연결 상태 감지를 사용하여 참가 상태를 정리한다.
게임, 초대, 채팅 데이터에는 저장 상한 또는 정리 정책을 둔다.
규칙으로 가능한 보호와 별도 서버가 필요한 보호를 정확히 구분한다.

프런트엔드에 Firebase Admin 자격 증명이나 서비스 계정 키를 넣지 않는다.
Firebase 웹 설정과 비밀 키의 차이를 README에 설명한다.
.env.example을 제공하고 실제 환경 파일은 Git에서 제외한다.

[11. 무료 운영과 성능]

렌더링 주기와 네트워크 전송 주기를 분리한다.
필요한 방과 게임만 구독하고 퇴장 시 해제한다.
전체 DB나 모든 방의 상세 상태를 구독하지 않는다.
방 목록은 작은 인원 요약 데이터만 사용한다.

다음 조건별로 트래픽을 추정한다.
- 같은 방의 2명, 4명, 8명
- 위치 전송 빈도
- 위치 데이터 크기
- 이동한 시간과 접속 시간
- 수신자 수에 따른 다운로드 증가
- 초기 구독과 재연결 비용

예상치는 가정과 계산식으로 제시한다.
무료 한도에 가까워지면 어떤 설정을 줄일지 문서화한다.

목표 성능은 일반적인 PC 브라우저에서 부드러운 이동이다.
저사양 기기를 위해 해상도, 픽셀 비율, 그림자 품질을 조절할 수 있게 한다.

[12. 개발 단계]

1단계: 로컬에서 홈과 공원 맵 구현
- 캐릭터 꾸미기와 미리보기
- 3D 그래픽 방향
- 방향키 이동, 충돌, 카메라
- Firebase 없이 실행 가능한 명시적 로컬 모드

2단계: 실제 멀티플레이
- 익명 인증
- 입장과 퇴장
- 참가자와 위치 동기화
- 연결 끊김과 재연결
- 기본 Security Rules

3단계: 소셜 기능
- 채팅과 말풍선
- 음소거와 도배 제한
- 이모트
- 나머지 4개 맵과 맵 변경

4단계: 가위바위보
- 초대, 선택 보호, 결과, 이탈, 재대결

5단계: 오목
- 초대, 착수 동기화, 승패, 기권, 이탈

6단계: 배포 준비
- 성능과 무료 사용량 검토
- Security Rules 최종 검증
- 타입 검사, 핵심 테스트, 프로덕션 빌드
- GitHub와 Vercel 배포 안내

각 단계의 완료 기준을 검증한 뒤 다음 단계로 진행한다.
검증 실패를 남겨둔 채 기능만 계속 추가하지 않는다.
매 단계마다 별도의 승인을 반복해서 요청할 필요는 없다.
제품 방향을 크게 바꾸거나 외부 작업이 필요한 경우에만 확인한다.

[13. 검증과 산출물]

중요 검증:
- 두 개 이상의 독립 브라우저 세션으로 실제 상호작용 확인
- 다른 방의 데이터가 섞이지 않는지 확인
- 동시 입장과 정원 처리 확인
- 새로고침과 연결 끊김 확인
- 한글 채팅 입력 확인
- 가위바위보 선택 노출과 공개 절차 확인
- 오목 중복 착수, 차례, 승리 판정 확인
- 허용되지 않은 Firebase 쓰기가 거부되는지 확인

검증을 실행하지 못했다면 그 사실을 명시한다.
